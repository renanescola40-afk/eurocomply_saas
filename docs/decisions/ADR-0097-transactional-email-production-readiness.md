# ADR-0097: Fail closed Production readiness on transactional email binding

- Status: Proposed
- Date: 2026-08-22
- Scope: protected Vercel Production deployment, `GET /api/ready`, and Resend transactional-email configuration

## Context

RISCK COMPLY already implements server-side transactional email through Resend for onboarding, invitations, billing and operational notifications. The delivery implementation reads `RESEND_API_KEY` and `EMAIL_FROM`, but the canonical protected Production deployment previously did not synchronize that provider/sender pair into Vercel Production, and `/api/ready` did not include transactional-email configuration in its final decision.

That created a release-policy gap: a deployment could be reported ready while workflows that depend on transactional email were unable to send because the provider key or reviewed sender was absent. Historical delivery evidence does not prove the current Production deployment is bound to Resend, and source-code presence does not prove provider availability, sender-domain verification or successful inbox delivery.

This change is configuration/readiness governance only. It does not send an email, inspect a provider credential, prove a Resend account or plan, prove sender-domain verification, prove delivery to Gmail/Outlook, or establish account-specific DPA, entity, region, retention or transfer facts.

## Decision

The canonical protected Production deployment will make transactional-email configuration a fail-closed readiness requirement by:

- forcing `REQUIRE_TRANSACTIONAL_EMAIL_DELIVERY=true` in the protected Production workflow;
- requiring `RESEND_API_KEY` from the protected Production secret store;
- requiring `EMAIL_FROM` from the protected Production variable store;
- synchronizing the Resend API key into Vercel Production as a sensitive server value;
- synchronizing the sender and readiness guard as server environment values that are not browser-exposed;
- making `/api/ready` return HTTP 503 when the guard is active and either required binding is absent or blank;
- exposing only boolean configuration state (`required`, `configured`, `apiKeyConfigured`, `senderConfigured`) and never returning provider values;
- performing no provider network request and sending no email as part of readiness.

Local and preview environments may leave `REQUIRE_TRANSACTIONAL_EMAIL_DELIVERY=false`. The canonical protected Production path is authoritative for enabling the fail-closed requirement.

## Operational failure mode

When the protected Production guard is active and either `RESEND_API_KEY` or `EMAIL_FROM` is absent/blank, `/api/ready` returns `503 not_ready` even if unrelated dependencies remain healthy.

This status means the configured release does not satisfy the declared Production transactional-email dependency. It does **not** by itself prove a Resend outage, provider suspension, domain-authentication problem, customer-impacting delivery failure or network failure because readiness intentionally performs no external Resend request.

Operators should distinguish:

1. **Configuration not ready** — one or both required runtime bindings are absent. Restore the reviewed provider-store values and redeploy through the protected workflow.
2. **Provider/runtime delivery incident** — configuration is present but real authorized delivery fails. Treat that as a separate operational/provider incident and use delivery logs/provider evidence; `/api/ready` is not a synthetic-email monitor.
3. **Domain/sender verification issue** — the configured sender exists but provider-side authentication is not accepted. Correct provider/DNS configuration and retain provider evidence before claiming delivery readiness.

## Security and privacy impact

The guard strengthens fail-closed release behavior without changing tenant isolation, RLS, RBAC, billing authority, authentication, email contents or database schema.

The readiness response intentionally contains booleans only. It must not return the Resend API key, sender value, provider account identifiers or other credentials. The protected workflow must not print provider values while synchronizing them.

No customer data, email body, recipient address or delivery event is generated by this readiness check.

## Risks and trade-offs

- A Production deployment with an incomplete email binding will become not-ready even when the web application, database and billing dependencies are otherwise healthy. This is intentional because transactional email is part of the declared Production operating contract.
- Configuration presence is weaker than end-to-end delivery proof. A green readiness result must not be marketed as successful inbox delivery, domain verification or provider availability.
- Treating email as a readiness dependency can lengthen recovery if the configuration store is damaged. The preferred recovery is to restore the reviewed binding, not to silently bypass the control.
- The policy depends on the protected Production workflow being the canonical deployment authority. Direct or ad-hoc deployment paths must not be used to claim Enterprise readiness.
- Provider-account, privacy and contractual facts remain separate External Assurance evidence and are not inferred from this technical binding.

## Incident handling and rollback

The normal recovery for a missing binding is:

1. verify the intended `EMAIL_FROM` against the reviewed sender configuration;
2. restore `RESEND_API_KEY` and/or `EMAIL_FROM` in the protected Production provider stores without exposing values;
3. deploy the exact approved release through the protected Production workflow;
4. re-run authenticated `/api/ready` evidence and confirm the exact deployed SHA;
5. separately perform authorized delivery proof only when required.

If the fail-closed policy itself must be rolled back during an incident, the rollback must be an explicit reviewed code/workflow change that reverts this ADR's implementation. Do not disable the guard through an undocumented ad-hoc environment mutation and do not bypass protected deployment governance.

While the guard is intentionally disabled or reverted, transactional-email readiness is no longer proven. Enterprise/Production assurance must record that limitation and must not treat the release as satisfying this control until the reviewed fail-closed policy and binding evidence are restored.

Because this decision adds no schema or data migration, rollback does not require database rollback, data repair, provider deletion, credential disclosure or customer-data mutation.

## Verification and evidence

The implementation is covered by:

- focused unit tests for guard-disabled, key-missing, sender-missing and complete-binding states;
- a regression contract requiring the Production workflow to bind `RESEND_API_KEY`, `EMAIL_FROM` and the guard consistently;
- strict public-secret scanning that rejects secret-shaped committed values;
- workflow governance and Actionlint;
- CI, security, CodeQL/SAST, DAST and Production-gate checks on the exact pull-request head.

After merge, repository checks remain insufficient to promote `RESEND_CURRENT_PRODUCTION_BINDING` by themselves. Promotion requires exact Production deployment evidence showing the guarded release is live and the runtime configuration/readiness evidence is attributable to that release. No real email is sent by this ADR or by the configuration readiness check.
