# Enterprise 100% Closure

The product must not be described as `Enterprise 100%` from repository preparation, merged pull requests or a successful deployment alone.

## Final decision rule

The closure returns `GO` only when every required evidence document:

- exists;
- is valid JSON;
- contains an explicitly accepted status or decision;
- identifies the exact promoted commit SHA;
- belongs to the same release candidate;
- is not explicitly marked as containing sensitive values;
- is not contradicted by a different exact-SHA document for the same required evidence path.

```bash
ENTERPRISE_CLOSURE_EXPECTED_SHA=<promoted-sha> \
ENTERPRISE_CLOSURE_EVIDENCE_ROOTS=<comma-separated-exact-sha-evidence-roots> \
node scripts/release/check-enterprise-100-closure.mjs
```

The result is written to:

```text
release-validation/enterprise-100-closure.json
```

## Required domains

The closure contract currently requires evidence for:

1. repository quality;
2. production deployment;
3. production smoke tests;
4. Supabase RLS reconciliation;
5. live tenant isolation;
6. backup and isolated restore;
7. rollback rehearsal;
8. observability runtime;
9. billing runtime;
10. legal publication acceptance;
11. final Go/No-Go approval.

## Exact-SHA retained artifact fan-in

A clean Git checkout does not contain runtime artifacts generated by other GitHub Actions workflows. Treating those files as permanently missing produced a structural `0/11` result even when retained proof existed outside the repository checkout.

`Enterprise 100 Closure` now performs a read-only fan-in on `main`, `workflow_run` and manual executions:

1. resolve the assessed SHA;
2. verify it is current `main` or an immutable ancestor of current `main`;
3. enumerate retained GitHub Actions artifacts with `actions: read` only;
4. accept only non-expired artifacts whose `workflow_run.head_sha` equals the assessed SHA exactly;
5. download only an explicit allowlist of evidence-producing artifact families;
6. extract them into an isolated source directory;
7. hydrate only evidence paths declared by `config/enterprise-100-closure.json` or an explicit semantic adapter listed below;
8. independently evaluate the accepted status/decision and exact-SHA binding.

The artifact allowlist includes the production final bundle, recovery drill, enterprise runtime closeout, readiness scorecard, Stripe billing validation, Supabase migration dry-run review bundle, final legal publication gate and conversation runtime closeout. Arbitrary same-SHA artifacts are not downloaded into the closure evidence pool.

Hydration is discovery, not approval. A hydrated document with `BLOCKED`, `OPEN`, a failed outcome, a non-accepted decision or another fail-closed outcome remains a blocker.

## Explicit semantic evidence adapters

Several long-lived runtime proofs predate the conceptual filenames in `config/enterprise-100-closure.json`. The hydrator therefore contains a **small reviewed allowlist**, not fuzzy filename matching:

| Closure control | Canonical retained source |
| --- | --- |
| production deployment | `docs/security/evidence/runtime/deployment-smoke-validation.json` |
| production smoke | `docs/security/evidence/runtime/authenticated-production-smoke.json` |
| live tenant isolation | `docs/security/evidence/runtime/supabase-live-rls-validation.json` |
| backup and restore | `recovery-source.json` |
| rollback rehearsal | `rollback-source.json` |
| observability runtime | `docs/security/evidence/runtime/observability-production-validation.json` |
| billing runtime | `docs/security/evidence/runtime/stripe-billing-validation.json` |
| final Go/No-Go | `docs/security/evidence/runtime/release-go-no-go.json` |

These mappings only make an already-existing source document discoverable under the conceptual closure path. They do not copy a PASS status into the document or bypass its own producer-side validator.

There is intentionally **no adapter** for `repository-quality` or `supabase-rls-reconciliation` until a canonical exact-SHA source with the same semantics is identified. Live tenant isolation is not treated as migration/RLS reconciliation merely because both concern Supabase.

## Status and SHA normalization

The checker recognizes the evidence bindings already used by repository proof contracts, including `targetSha`, `expectedSha`, `commitSha`, `releaseSha`, `deploymentSha`, `sourceSha`, `productSha`, `buildSha`, `sha`, `provenance.commitSha`, `provenance.targetSha` and `reviewBinding.productSha`.

Status normalization is deliberately narrow:

- `status: Complete` plus a passing `outcome`/`validationStatus` normalizes to `PASS`;
- `Complete` plus `failed` does **not** normalize to PASS;
- explicit release/human decisions such as `finalDecision: Go` and `publicationStatus: COUNSEL_ACCEPTED` take precedence over a generic status field;
- every resulting value still has to appear in that control's existing `acceptedStatuses` allowlist.

This lets the closure understand canonical proof schemas without weakening their semantics.

## Hydration safety contract

`scripts/release/hydrate-enterprise-100-evidence.mjs` never creates runtime or human evidence. It classifies each declared evidence item as one of:

- `HYDRATED` — one exact-SHA document, or multiple byte-identical copies, was found;
- `MISSING` — no usable retained document was found;
- `STALE` — candidates exist but belong to another SHA;
- `REJECTED_SENSITIVE` — exact-SHA evidence is explicitly marked as containing sensitive values or unredacted secrets;
- `AMBIGUOUS` — two or more different documents claim the same evidence path and exact SHA.

The manifest also records whether a successful hydration used the declared path or an `explicit_alias`. No unlisted filename similarity is accepted.

The hydration manifest is retained at:

```text
artifacts/enterprise-100-evidence-root/enterprise-100-evidence-hydration.json
```

## Progressive reevaluation

Runtime and human evidence producers finish at different times. The closure reevaluates after relevant workflows complete, including production, recovery, provider, readiness, Stripe, Supabase and the **Final Legal Publication Gate**.

Runs for the same SHA use `cancel-in-progress: false`. One producer finishing therefore cannot kill a closeout already reading another producer's artifact. Later queued runs can observe a more complete retained-artifact set and produce a progressively more informative `NO_GO` or, only when every control genuinely passes, `GO`.

The initial push run may therefore be `NO_GO` while proof producers are still running. That is expected and must not be bypassed.

## Fail-closed behaviour

The following always prevent closure credit:

- missing or invalid JSON;
- stale or different-SHA evidence;
- sensitive/unredacted evidence;
- conflicting exact-SHA evidence;
- a status or decision outside the control's accepted-status allowlist;
- missing required human/legal acceptance;
- missing runtime proof;
- placeholders, templates or repository preparation presented as runtime evidence.

A CI variable, successful workflow, merged PR, deployment, generated template or artifact presence alone cannot substitute for required evidence semantics.

## Pull-request validation

PR execution validates the checker, hydrator and workflow contracts only. It does not download production artifacts and cannot produce Enterprise GO.

The workflow is read-only and uses immutable action pins. It has no deployment, database, billing, secret-management or production-write permission.

## Operational boundary

This closure orchestration does not:

- deploy to production;
- execute Supabase migrations or SQL;
- mutate customer data;
- create Stripe products or prices;
- modify Vercel configuration;
- change branch protection;
- perform backup/restore operations;
- approve legal or qualified human-review evidence;
- auto-merge pull requests.

Those controls remain separate operator/provider/human responsibilities where applicable.

## Current truthful status

Repository-controlled implementation is advanced, but Enterprise 100% remains `NO_GO` until all eleven control domains have accepted, exact-SHA evidence for the same release candidate. The fan-in removes evidence-discovery plumbing errors; it does not change the underlying readiness standard.
