# ADR — Protected production rollback proof

## Decision

Production rollback evidence must be generated only by an explicitly dispatched GitHub Actions job using the protected `production` environment. The requested current release must still be the exact `main` SHA when the job starts, and the operator must confirm both the current and target SHA in the dispatch input.

The job performs an actual Vercel instant rollback to a distinct previously healthy production deployment, validates `/api/health`, `Cache-Control: no-store`, and the target build SHA, then restores the current deployment with `vercel promote` and repeats the health and SHA assertions.

## Safety boundary

The workflow is never triggered by pull requests or normal pushes. Concurrency does not cancel an in-flight recovery exercise. Missing secrets, an unapproved environment, stale `main`, an identical target, invalid confirmation, failed rollback, failed health, failed restoration, or a mismatched build SHA leaves the evidence open and exits non-zero.

The evidence records booleans, statuses and provenance only. It does not persist Vercel tokens, deployment URLs, authorization headers, cookies or provider responses.

## Scorecard boundary

Repository checks prove only that the protected mechanism is fail-closed. REC-01 through REC-04 remain `NOT_VERIFIED` until an eligible human authorizes a real production exercise and the exact-main-SHA artifact is independently validated and consumed by the Enterprise Readiness Scorecard.

Backup, restore, data-integrity, post-restore RLS, RPO and RTO controls are outside this change.

## Rollback

Revert the workflow, runner, tests and this decision. Delete any artifact generated by a reverted or failed exercise. Reverting must not preserve a PASS claim for production rollback readiness.
