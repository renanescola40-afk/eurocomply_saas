# Final validation evidence state machine

Date: 2026-07-15  
Status: Proposed

## Context

The canonical `final-validation-runner.json` placeholder declared `status: Open` and `outcome: failed`. The Enterprise Readiness Scorecard therefore reported a proven failure even though no final production validation run had occurred.

The writer used by the release process already emitted `Open / blocked`, but its `Complete` output could not satisfy the validator because it omitted required provenance and integrity fields and wrote `failures` as an object instead of the required array.

A subsequent coherence review found that a superficially valid `Complete` document could still contain a non-numeric run identifier, divergent target/commit/build SHAs, incomplete source evidence, an open runtime register, unresolved blocking arrays, or a non-enterprise target.

This created three integrity problems:

1. missing proof was represented as a failed execution;
2. even a genuinely successful final run could not produce evidence accepted by the canonical validator;
3. a manually assembled document could assert `Complete / Go` while its internal provenance and source state were contradictory.

## Decision

Use an explicit final-validation state machine:

- `Open / blocked` or `Open / not_verified`: required proof is incomplete and release decision is not Go;
- `Exception / blocked` or `Exception / not_verified`: a time-bounded exception exists and release decision is not Go;
- `Complete / passed / Go`: every required command and source evidence passed with trusted, internally coherent provenance;
- `Complete` with any other outcome or decision is invalid.

The final evidence writer now:

- exports a pure builder so writer output can be tested directly against the validator;
- emits `failures` as an array and keeps structured details under `blockingReasons`;
- records `runtimeContext`, `releaseDecision`, all required evidence-integrity flags, source states, register state, and the exact commit/build identity;
- permits `Complete` only when generated by GitHub Actions for `renanescola40-afk/eurocomply_saas`, branch `main`, with a numeric run ID;
- requires release target `enterprise`;
- requires target, commit, runtime, and build SHA to be full 40-character values and identical;
- requires production-final and enterprise-runtime evidence to be `Complete / passed`;
- requires release Go/No-Go evidence to be `Complete / Go`;
- requires the runtime evidence register and every structured blocking array to be empty;
- remains `Open / blocked / No-Go` for local runs, feature branches, missing commands, mismatched builds, non-enterprise targets, open register items, unresolved blockers, or incomplete source evidence.

The validator independently enforces the same requirements. Writer output is not trusted merely because it was produced by the repository script.

## Impact

The scorecard can distinguish a blocked, not-yet-proven release from an actual failed validation. Release enforcement remains fail closed: `check-enterprise-runtime-evidence.mjs` still requires `status: Complete`, and Open evidence cannot permit release.

A future successful production-final execution can now generate an internally coherent bundle that the canonical validator accepts. This PR does not execute production validation and does not create Complete evidence.

REL-10 is expected to move from `FAIL` to `NOT_VERIFIED`, with no score increase and no reduction in critical-open controls.

## Verification

Repository tests cover:

- valid Open, Exception, and Complete states;
- rejection of Open/failed and Open/Go contradictions;
- stale and placeholder evidence;
- feature-branch provenance;
- non-numeric GitHub run identifiers;
- missing and duplicate commands;
- non-enterprise release targets;
- expected-SHA and internal SHA divergence;
- incomplete source evidence;
- open register items and unresolved blocking reasons;
- stored raw URLs;
- writer-to-validator compatibility;
- writer refusal when GitHub provenance, build SHA, or release target is invalid.

## Evidence boundary

Repository tests prove the state machine and writer/validator compatibility. They do not prove deployment health, Supabase RLS, Stripe, Sentry, rollback, restore, branch protection, external security review, legal review, or production release approval.

## Risks and trade-offs

- historical consumers that interpreted `outcome: failed` on an Open placeholder must use the explicit status/outcome state machine;
- GitHub Actions provenance is intentionally required for final Complete evidence, so local readiness can diagnose blockers but cannot author final release proof;
- a successful workflow still depends on the correctness and freshness of each upstream runtime evidence writer;
- the committed placeholder review timestamp reflects this schema correction, not a production validation run.

## Rollback

Revert this change to restore the old writer and placeholder. That rollback also restores the impossible writer/validator Complete contract and the misleading Open/failed scorecard result, so it should only be used with an equivalent replacement.
