# ADR — Generated exact-SHA P0 runtime evidence register

- **Date:** 2026-08-04
- **Status:** Accepted
- **Owners:** Release Engineering and Security Engineering

## Context

`docs/security/P0_RUNTIME_EVIDENCE_REGISTER.md` was created as a manual release worksheet. Its status cells could remain unchanged for weeks while canonical runtime evidence, validators, workflows and the assessed `main` SHA continued to evolve.

That created two conflicting truths:

1. the canonical evidence files and validators;
2. a human-maintained Markdown status table.

A stale `Open` row could understate completed work. More dangerously, a stale or manually edited `Complete` row could appear to overstate readiness even when the evidence was missing, malformed, stale, placeholder-only or bound to another SHA.

## Decision

The versioned Markdown file is now policy metadata only. It records:

- canonical control names;
- required evidence;
- owners;
- next actions.

Every versioned row remains fail-closed `Open`.

Current status is generated by `scripts/security/generate-p0-runtime-evidence-register.mjs` for one exact 40-character SHA. The generator:

- consumes the canonical catalog;
- invokes the existing canonical runtime validators;
- validates deterministic repository controls from the assessed checkout;
- treats the Markdown status as advisory diagnostic metadata only;
- records drift between legacy metadata and derived status;
- produces JSON and Markdown artifacts;
- signs the semantic result with a SHA-256 digest;
- returns `GO` only when every active P0 control is `Complete`.

`scripts/security/validate-generated-p0-runtime-evidence-register.mjs` independently validates counts, control identity, status consistency, decision semantics, exact SHA and integrity digest.

## Truth rules

1. A Markdown word never proves a runtime control.
2. Runtime controls pass only through their canonical validators.
3. Repository controls are recalculated from the exact checkout.
4. Missing, malformed, stale, wrong-SHA and placeholder evidence fail closed.
5. `Exception` cannot be created by changing the policy table.
6. The generated artifact is immutable workflow output, not a committed moving snapshot.
7. `GO` requires zero blocking controls.

## Consequences

### Positive

- Status cannot drift silently from canonical evidence.
- Release owners receive exact blocker diagnostics for every SHA.
- Repository documentation stops claiming a current decision long after it becomes stale.
- PR and `main` workflows produce comparable evidence artifacts.
- Existing specialist validators remain authoritative.

### Trade-offs

- The committed policy table always looks `Open` by design.
- Operators must inspect the generated artifact for current status.
- A newly merged commit requires a new artifact even when the prior SHA passed.
- Provider and external evidence still require real execution or qualified human review.

## Non-goals

This decision does not:

- generate provider evidence;
- execute a pentest;
- approve a legal review;
- modify Vercel, Supabase, Stripe, Sentry or GitHub settings;
- declare Enterprise GO without exact-SHA proof.

## Rollback

Revert the generator, validator, workflow and policy documentation together. Do not restore manual `Complete` statuses without also restoring the old release semantics and accepting the documented drift risk.
