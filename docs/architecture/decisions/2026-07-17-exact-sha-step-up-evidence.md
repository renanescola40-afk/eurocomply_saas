# Exact-SHA evidence for sensitive-action step-up

- **Date:** 2026-07-17
- **Status:** Proposed
- **Control:** IAM-08 — Sensitive-action step-up validated
- **Scope:** Repository implementation and exact-SHA execution evidence

## Context

RISCK COMPLY already has a centralized step-up boundary for high-risk actions. The implementation includes provider challenges, Supabase MFA or enterprise-IdP verification, short-lived signed tokens, user/organization/action scoping, persistent nonce records, single-use consumption, replay rejection, no-store denial responses and audit events.

The enterprise scorecard still referenced `docs/security/evidence/p1/step-up-sensitive-actions.json`, but that file could only be produced from a manually prepared input. This created two bad outcomes:

1. IAM-08 remained permanently `NOT_VERIFIED` even when the repository implementation and exact-SHA security suite were healthy; or
2. a manually completed checklist could be mistaken for proof that production MFA or AAL2 had actually executed.

## Decision

Generate the IAM-08 evidence inside the Enterprise Readiness Scorecard workflow after the exact-SHA GitHub checks have been captured.

Promotion to `Complete/passed` requires all of the following:

- canonical repository and GitHub Actions provenance;
- exact target SHA equal to the checked-out SHA;
- Full Security Suite and aggregate required checks passing for that SHA;
- centralized signed-token, expiry, scoping, persistence, replay and audit contracts present;
- real provider challenge and verification boundaries present;
- token and challenge migrations enforce short expiry, service-role access and RLS;
- every tracked billing, export, team-management, GDPR, audit and security-settings route awaits `requireStepUpForRequest` with the correct high-risk action;
- negative, expiry, scope, tamper and replay tests remain present and pass through the exact-SHA suite;
- no secrets, tokens, credentials or customer data are copied into evidence.

The generated document retains the legacy P1 evidence fields so existing strict checkers and release gates continue to validate it.

## Evidence boundary

IAM-08 proves the repository enforcement boundary and exact-SHA execution of its tests. It does **not** prove:

- production Supabase MFA configuration;
- a production AAL2 session;
- enterprise IdP configuration;
- administrator MFA policy completion;
- SAML/OIDC SSO completion;
- provider availability or production tenant data.

Those claims remain gated by the protected Step-Up Runtime Proof and the separate IAM-07 and IAM-09 controls.

## Security consequences

### Positive

- A route losing or mis-scoping step-up causes evidence generation to fail closed.
- A replay, expiry, migration or provider-boundary regression is tied to the same SHA as the scorecard.
- Manual boolean statements cannot promote IAM-08.
- Runtime provider claims remain separate and cannot be inferred from repository evidence.

### Trade-offs

- The evidence builder intentionally duplicates a small set of security-critical source contracts already checked by `security:step-up`.
- New sensitive routes must be added to the tracked route policy list before IAM-08 can remain complete.
- Production release still blocks when provider configuration or live runtime proof is absent.

## Rollback

Revert the evidence builder, its tests and scorecard workflow integration. Remove any IAM-08 PASS generated by this mechanism and return the control to `NOT_VERIFIED`. Do not retain the generated P1 evidence as proof after rollback.
