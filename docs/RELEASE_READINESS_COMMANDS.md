# Release Readiness Commands

This document lists the commands used to validate RISCK COMPLY before promoting a build to production or enterprise review.

## Current status

As of 2026-07-11, implementation hardening is **99%**. Public production and enterprise promotion remain **No-Go** until their respective gates have real evidence for the exact promoted commit.

## Release gate separation

Public production readiness and enterprise procurement readiness are separate contracts:

```bash
npm run release:readiness
npm run release:enterprise-readiness
```

`release:readiness` validates public-production operational controls and runtime evidence. It does not claim or require external pentest/review evidence.

`release:enterprise-readiness` runs the canonical enterprise release target. External review/pentest evidence, or a formally approved enterprise exception with owner and expiry, remains mandatory for enterprise promotion.

This separation does not weaken security. It prevents an enterprise-only evidence requirement from being misrepresented as a public-production runtime failure while preserving fail-closed enterprise controls.

## Canonical final gate

Use the canonical release command for the selected release target:

```bash
npm run release:production-final
```

This gate expands into deterministic install, lint, typecheck, tests, production-like E2E, build, security checks, live RLS validation, deployment smoke, observability smoke, rollback dry-run, release evidence aggregation and strict P0 runtime gap validation.

For enterprise promotion use:

```bash
npm run release:enterprise-readiness
```

## Required repository controls

- `package-lock.json` aligned with `package.json`.
- CI green for the exact promoted commit.
- Public exposure scanning enabled in strict fail-closed mode.
- Any high or critical audit finding fixed or triaged.
- Production smoke evidence generated from the real deployment URL without exposing sensitive values.
- Release environment readiness evidence generated by the runtime runner.

## Enterprise blocking CI

Every enterprise release candidate must have a green GitHub Actions run for the Enterprise Production Gate or an equivalent workflow that invokes the canonical enterprise gate.

The blocking CI must run:

```bash
npm ci
npm run lint
npm run typecheck
npm run test
npm run build
npm run security:ci
npm run quality:routes
npm run release:enterprise-readiness
```

It may also run browser install, E2E, CodeQL, Dependency Review, OSSF Scorecard, branch-protection evidence validation and SBOM generation.

## Production smoke test

The deployment smoke command is still available as a component gate:

```bash
npm run release:deployment-smoke
```

The smoke test is fail-closed. It writes `docs/security/evidence/runtime/deployment-smoke-validation.json` and must not be called passed unless every critical check succeeds.

Required environment for runtime smoke includes a target deployment URL, a protected readiness token, commit/build metadata and rollback target metadata. Do not write raw token, cookie, authorization header or secret values into evidence.

The smoke command validates:

- Production URL is configured.
- `/api/health` returns healthy public status.
- `/api/ready` rejects anonymous access.
- `/api/ready` returns ready with the protected healthcheck token.
- Public landing, pricing, trust and login pages load.
- Protected dashboard routes require authentication.
- Protected redirects use no-store semantics.
- Security headers are present on public pages.
- Supabase, Stripe, Redis, Sentry, database connectivity and enterprise upload scanner readiness are confirmed through grouped readiness checks.
- Rollback target is configured and health-checked when it is a URL.
- Last commit and build SHA are registered in evidence.
- Observability smoke guard rejects anonymous requests and can emit a real protected smoke event when enabled.

## Component governance checks

These commands are component gates:

```bash
npm run release:readiness
npm run release:enterprise-readiness
npm run release:enterprise-runtime-evidence
npm run security:p0-runtime-gap:strict
```

Use `release:readiness` for public-production operational readiness. Use `release:enterprise-readiness` for enterprise promotion.

## Full security CI

Run `npm run security:ci` with strict public scanning enabled. This is the application security gate and must pass before public production.

It validates audit, lockfile alignment, production configuration readiness, routes, RLS checks, API guards, protected routes, client boundaries, auth token validation, authorization/BOLA controls, server action identity, security headers, no-store protections, origin guards, no-open-proxy controls, upload security, workflow governance, supply-chain controls and trust evidence.

## Supply-chain release steps

Before calling a release ready, collect:

```bash
npm run supply-chain:lockfile
npm run security:package-lock
npm run supply-chain:floating-deps
npm run security:npm-audit:json > npm-audit.json
node scripts/security/check-branch-protection-evidence.mjs
```

Then review and attach the generated lockfile, audit evidence, branch-protection evidence and SBOM artifact to the release package.

## Branch protection configuration evidence

If the GitHub branch protection or rulesets API is unavailable, configure the required checks manually:

```text
Settings -> Rulesets/Branches -> main -> required checks -> add every check listed in docs/security/BRANCH_PROTECTION_REQUIRED_RULES.md
```

Do not mark branch protection evidence `Complete` without API-generated or screenshot-backed proof.

## Public production promotion rule

Do not promote to public production unless all of these are true:

- CI is green for the exact commit.
- `npm run security:ci` passes.
- `npm run release:readiness` passes in the configured production environment.
- `deployment-smoke-validation.json` is `Complete/passed` for the exact deployed URL.
- `observability-smoke-validation.json` is `Complete/passed`.
- `rollback-dry-run-validation.json` is `Complete/passed`.
- `supabase-live-rls-validation.json` is `Complete/passed` for the target project.
- Branch protection evidence is `Complete/passed`.
- Vercel build/deploy is green.
- Billing/webhook checks are attached.
- SBOM artifact is attached.
- Any high/critical audit item is fixed or triaged with owner and expiry.
- Any remaining exception is documented with owner and expiry.
- `release-go-no-go.json` says `finalDecision: Go`.

## Enterprise promotion rule

Do not promote to enterprise unless the public-production requirements also pass and external review/pentest evidence is real and complete, or a formal enterprise exception is approved and recorded with owner and expiry.
